# 详细设计说明书 Word 规格

## 一、整体结构（严格按基础模板，只输出有正文的部分）

```
封面（本资料仅供内部使用！／系统名／项目名／详细设计说明书／日期）
修改记录（表格：制定日期｜内容摘要｜版本｜拟稿）
目录（TOC 域，只收七、及其下级）
七、模块设计（功能设计细化）── 1..N 各业务功能
```

**硬性规定**：基础模板中一至六章（简介、总体设计、模型/数据库设计、接口设计、功能设计、模块命名规则）与八至十三章（用户界面规范、安全性、系统性能、备份设计、恢复设计、系统出错处理设计）在模板正文中均为空白，只有目录条目、没有内容。

因此本技能**只生成第七章**，其余章节一律不生成、不补写、不新增。不得以"设计文档应当完整"为由添加模板以外的章节，也不得新增模板中没有的小节（例如"数据加工映射文档""非功能需求"之类）。

判断标准：**模板里有的才写，模板里没有的一律不写**。封面、修改记录、目录属于模板既有内容，保留；修改记录与目录不进入目录本身（不设大纲级别）。

## 二、第七章：每个模块的固定 7 段

```
N. <业务功能标题>
   ┌ 需求描述（约 150 字，紧贴标题，无小标题）
   ├ 1) 操作界面      → 一律填「无。」
   ├ 2) 模块流程      → 约 150 字
   ├ 3) 关联模块      → 一般填「无。」
   ├ 4) 设计说明      → 约 150 字
   ├ 5) 引用的数据库表 → 表格：数据库｜数据库用户｜表英文名｜表中文名
   └ 6) 测试要点      → 场景1、场景2 …（与 Excel 技术测试逐条对应）
```

### 2.1 需求描述（约 150 字）

写清四件事：面向什么业务对象、解决什么现状问题、提供哪些能力（列举 2–4 项）、达到什么管控目的。

参考句式：
> 本模块面向 XX 业务场景，现系统仅支持 A，缺少 B 与 C。本次通过新增 D、E 能力，支持按 F 维度查询与处理，并对 G 过程全程留痕，满足监管对可追溯的要求。

### 2.2 模块流程（约 150 字）

按"入口 → 检索 → 处理 → 校验 → 流转 → 回写 → 留痕"的时间顺序叙述，必须出现角色动作与系统动作的交替。

参考句式：
> 业务人员进入 X 菜单，按 A、B 条件检索待处理数据；进入处理页完成信息核对与内容录入；提交时系统执行完整性校验，缺失项定位提示；校验通过后按配置的流程节点流转至下一角色；处理结果回写主表并记录操作留痕。

### 2.3 设计说明（约 150 字）

必须体现技术分层，模板惯例是"展示层／服务层／数据层"或"前端组件／服务实现／数据权限"三段。

参考句式：
> 后端采用控制层、服务层、数据访问层三段结构，业务规则集中在服务层，状态流转由状态机统一管控，非法操作在服务端拦截。前端以组合式组件复用列表与表单，权限通过路由守卫与按钮级指令双重控制。数据层按机构维度建索引并做权限裁剪。

### 2.4 引用的数据库表

表格四列：`数据库`、`数据库用户`、`表英文名`、`表中文名`。只列本模块真正读写的表，一般 2–4 张。

- `数据库` 固定 `Oceanbase`；`数据库用户` 由系统决定：**反洗钱管理系统2.0 填 ams，反洗钱客户尽职调查管理系统填 amd**，与 `project.db_user` 一致，同文档内不得混用。
- `表英文名` 优先取真实表结构字典（`assets/aml_tables.json`）中的原名，保留大写与下划线，如 `T5A_BLACK_LIST`、`T1B_DCI`、`T2A_CASE_CUST_CUR`；本期新增的表才自拟，前缀跟随所属章节（05 章用 `T5A_`、02 章用 `T2A_`、10 章用 `T00_`）。
- `表中文名` 沿用字典中的名称，如 `T5A_黑名单信息`；新增表的中文名以业务含义命名，简明即可。

选表与取字段用脚本，不要凭印象编：

```bash
python scripts/aml_tables.py list --module 05 --keyword 名单
python scripts/aml_tables.py show T5A_BLACK_LIST
python scripts/aml_tables.py pick T5A_BLACK_LIST T5A_BLACK_LIST_LOG --user ams
```

引用真实表时，`设计说明` 与 `测试要点` 要用真实字段取证，例如"按 `LIST_STS` 名单状态（1 待审核 / 2 审核通过 / 3 退回）控制流转"，这比泛泛描述更有说服力；字段名必须与字典一致。

### 2.5 测试要点（与 Excel 技术测试对应）

编号句式与 Excel 技术测试同源：`场景N：<角色>进入<菜单-子菜单>，<前提数据>，<执行动作>，查看<观察点>是否<预期>`。编号从 1 连续，不用 `1)、`。

条数是**模块级汇总**，不等于该模块所有功能行场景数之和：单功能模块可近似照搬该功能行场景；多功能模块从各功能行中挑模块级关键路径，**7–15 条**，且走通路径与拦截异常两类都要有。详细写法见 `references/test-case-spec.md`。

覆盖维度（按模块实际情况取用，不适用则跳过）：

1. 表结构与索引核对（含字段取值）
2. 页面/菜单权限与数据范围
3. 查询条件组合与默认排序
4. 校验与拦截提示
5. 流程流转与状态回写
6. 批量/跑批与重试
7. 留痕与日志可追溯
8. 跨机构越权拦截

样例（可直接借鉴句式）：
> 场景1：分行操作员登录反洗钱系统，进入风险任务处置，查看查询条件和列表显示，设置不同查询条件进行查询，查看查询结果与流程状态是否正确
> 场景2：分行操作员选择待处置的风险任务，填写处置意见并提交，查看提交后流程流转是否正常、任务状态是否回写
> 场景3：无处置权限的角色进入风险任务处置，查看菜单与操作按钮是否隐藏

## 三、排版参数

| 项目 | 值 |
|---|---|
| 纸张 | A4，上下 2.54cm，左右 3.17cm |
| 正文 | 宋体 + Times New Roman，10.5pt，1.5 倍行距，首行缩进 2 字符 |
| 一级标题 | 黑体 15pt 加粗，`一、 标题` |
| 二级标题 | 黑体 13pt 加粗，`1. 标题` |
| 三级标题 | 黑体 12pt 加粗，`1) 标题` |
| 表格 | Table Grid，表头加粗居中，正文 9pt |
| 页脚 | 居中：文档名 + 第 X 页（PAGE 域） |
| 目录 | TOC 域 `\o "1-3" \h \u`，打开后按 F9 更新 |

## 四、与 Excel 的一致性硬约束

| 项 | 要求 |
|---|---|
| 模块数 | = Excel 系统模块数 = 需求文档业务功能条目数 |
| 模块名 | 逐字一致，含长标题（"增加支持…""和调整…"） |
| 模块顺序 | 与需求文档一致 |
| 测试要点 | 与 Excel 技术测试场景逐条对应，不得出现 Excel 里没有的测试对象 |
| 表名 | 与 Excel 开发段"涉及表"一致，且与 `assets/aml_tables.json` 中的真实表名逐字一致 |
| 操作界面 | 一律「无」（本期均为菜单内页面改造，无独立界面交付） |
