# 工作量评估表 Excel 规格与文案范式

## 一、工作表构成（保持模板四页）

| 工作表 | 处理方式 |
|---|---|
| 填写说明 | 原样保留，不改 |
| 项目工作量评估表 | 本技能唯一填写对象 |
| 独立测试 | 保留模板结构，一般不填 |
| 产品采购评估表 | 原样保留 |

## 二、表头与列（第 1–4 行固定）

- 第 2 行（合并 B2:O2）：`项目工作量评估表（仅为科技侧工作量）`
- 第 3 行：`项目编号：`（B3:D3）／`项目名称：XXX`（E3:K3）／`系统名称：XXX`（L3:O3）
- 第 4 行表头：B 项目阶段｜C 系统模块｜D 功能（D4:E4）｜F 工作项描述（F4:K4）｜L 备注｜M 工作量(人天)｜N 合计(人天)｜O 任务描述

列宽（模板固定值，勿改）：B 16.9 / C 22.5 / D 12.5 / E 8.43 / F 9.38 / G–J 8.43 / K 33.56 / L 18.75 / M 13.75 / N 13.75 / O 40.88。
M、N 列数字格式 `0.0_ `，字体宋体 11，四边细边框。

## 三、行结构

```
段1 需求      ├─ 模块1 ├─ 功能1 (D:E / F:K / M)
              │        └─ 功能2
              ├─ 模块2 …
段2 设计      └─ 与需求完全相同的功能行清单
段3 开发      └─ 与需求完全相同
段4 技术测试  └─ 与需求完全相同
段5 性能测试  1 行：C=性能测试  D=性能测试方案与测试
段6 业务测试  └─ 与需求完全相同
段7 准生产    └─ 与需求完全相同
段8 上线支持  1 行：C=上线准备与投产支持  D=上线准备与投产支持
总计（人天）  B:C 合并标签，D:O 合并 =SUM(N5:N末行)
总计（人月）  B:C 合并标签，D:O 合并 =D{总计人天}/21.75
```

合并规则（生成时逐条落实）：

- B 列按**阶段块**合并（如 B5:B12），单行阶段不合并；
- C 列按**模块块**合并（如 C5:C6、C7:C8），单行模块不合并；
- 每行 D:E 合并、F:K 合并；
- N 列按**阶段块**合并，首格写 `=SUM(M首:M末)`；
- O 列仅两处写含义说明并跨阶段块合并：需求段与业务测试段（准生产段沿用同一说明时可不重复）。

O 列固定说明文案：

- 需求段：`含义:此部分仅包括科技外包人员将业务需求转化为软件需求需要的工作量，不含业务部门提出、编写需求规格说明书的工作量。`
- 业务测试段：`含义:此部分仅包括科技外包人员协助业务人员开展测试的工作量，不含业务部门编写案例、执行测试过程的工作量。`

## 四、功能列拆分原则

「功能」列可自由拆分（用户明确允许），拆分依据：

1. 一个业务功能内包含**多张页面/多个菜单**时，按页面拆；
2. 含**独立定时任务、独立接口、独立报表/导出**时，单独成行；
3. 需求文档中「业务规则」下若有 4 个以上子项（如数据预校验、核验结果反馈、实质差异化比对、二次核验、备案信息查询、核验次数上限），按子项聚合为 1–2 行；
4. 拆分后开发行必须仍在 3.5–9.5，若单行会超过 9.5，则必须再拆一行。

## 五、工作项描述文案范式（核心）

字体宋体 11，左对齐、垂直居中、自动换行。

### 5.1 需求段（6–10 条）

```
根据业务需求开展需求分析及需求澄清工作，同时进行技术可行性评估，主要包括以下需求内容：
1、<业务动作>：<具体规则/字段/条件/分支>；
2、……
```

写法要点：每条以"业务名词 : 说明"结构，说明里必须出现**具体字段名、状态值、机构类型、时间窗口、上限值**等可验证细节，不写"优化用户体验"这类空话。

### 5.2 设计段（6–10 条，三段式）

```
一、数据表设计
1、<表名>增加<字段>，历史数据按<规则>回填；
2、新增<XX表>：<关键字段列举>；
二、功能设计
1、<页面>支持<条件/交互>；
2、<详情页>按<分类>展示，<异常项>逐条列示；
三、权限设计
1、功能权限：<角色>可<动作>，<角色>不可；
2、数据权限：按<机构/岗位>控制，跨机构不可见；
3、留痕要求：<动作>全过程记录<要素>，日志不可删改。
```

### 5.3 开发段（6–10 条，三段式，末条列涉及表）

```
一、数据表开发
1、<表>建表/加字段脚本、索引脚本；
2、<基础数据>初始化脚本；
二、前端开发
1、<页面>：<组件、交互、校验>；
2、<组件>：<复用关系>；
三、后端开发
1、<查询接口>：<条件组合 + 数据权限 + 分页>；
2、<保存/提交接口>：<校验 + 状态流转>；
3、<定时任务/跑批>：<调度规则 + 重试>；
4、涉及表：TXX_A、TXX_B、TXX_C。
```

`涉及表` 与 Word 第七章「引用的数据库表」逐张一致，优先写真实表名（`T5A_BLACK_LIST` 这类，保留大写），不要自造小写表名。

### 5.4 技术测试段（首 2 条固定 + 按功能列场景）

```
1、梳理测试场景、编写技术测试案例；
2、开展技术测试案例评审，进一步完善测试案例；
3、测试人员根据测试案例进行测试，测试以下场景：
1)、核对<N>张表结构、索引与设计一致，<关键字段>取值正确；
2)、<页面>按<条件>查询，核对结果与直查一致、默认排序正确；
3)、构造<边界/异常数据>，核对<校验/拦截/提示>正确；
4)、非授权角色执行<动作>返回无权限，跨机构数据不可见；
5)、<留痕/日志>可按<流水号>追溯。
```

### 5.5 业务测试段（固定句式）

```
1、为业务测试工作准备相应测试环境及系统后台基础测试数据；
2、在业务测试人员测试的过程中，对测试出现的问题进行原因排查、问题解决，主要功能包括：
1)、核对<业务口径>与工作指引一致；
2)、核对<操作路径>符合业务习惯；
3)、核对<结果>可直接用于报送/答复。
```

### 5.6 准生产段（固定句式，短）

```
1、为准生产测试工作准备相应测试环境及系统后台基础测试数据；
2、在业务测试人员准生产测试的过程中，对测试出现的问题进行原因排查、问题解决，主要功能包括：<3–5 个关键词短语>。
```

### 5.7 性能测试段（全表 1 行，5–7 条）

```
1.与性能测试团队沟通，进行业务场景评测，沟通测试场景及测试方案
2.验证<核心交易>在<并发量>下的响应时延、成功率与资源占用
3.验证<批量/报表>在历史全量数据下的执行耗时
4.按照既定的交易占比进行测试，验证系统处理能力及服务器资源消耗情况
5.验证系统稳定运行 8 小时情况，是否存在内存泄漏等现象
```

### 5.8 上线支持段（全表 1 行，4 条）

```
1、准备镜像晋级，代码封版；
2、编写上云部署序列、监控告警配置等上线序列文件；
3、<参数/规则/模板>等基础数据投产初始化与核对；
4、配合进行投产支持，投产首日驻场保障及<核心链路>全链路验证。
```

## 六、自检清单

- [ ] 模块数量、名称、顺序 = 需求文档业务功能条目
- [ ] 每模块至少 1 个功能行；功能行在 8 个阶段中数量一致
- [ ] 需求/设计/开发每行 6–10 条编号
- [ ] 开发行全部在 3.5–9.5、步长 0.5、均值≈7.5、无 ≥10
- [ ] 全表无 0.4/0.3/0.25 以外的非 0.5 步长（技术测试允许 0.25）
- [ ] N 列各段合计 = 该段 M 之和；总计 = 各段之和；人月 = 总计/21.75
- [ ] 表头项目名称、系统名称已填写
