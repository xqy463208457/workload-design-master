# 测试编写规范（技术测试／业务测试／准生产）

本文件是 Excel 三段测试文案与 Word「6) 测试要点」的唯一写法依据。规范来自《科技侧工作量评估表-反洗钱管理系统2.0综合效能提升项目20250807-完整版.xlsx》中 22 条功能行的实际写法（该项目共 537.45 人天，技术测试 153.75 人天、业务测试 52.70 人天、准生产 26.25 人天）。动笔前必读，写完按第八节自查。

---

## 一、三段的分工

| 段 | 一句话定位 | 验证对象 | 典型观察点 |
|---|---|---|---|
| 技术测试 | 验证程序按设计跑通 | 表、接口、报文、任务、日志 | 字段取值、组包解析、索引、任务结果、留痕 |
| 业务测试 | 验证业务口径可接受 | 指引条款、业务习惯、结果可用性 | 分类是否正确、流程是否顺畅、结果能否直接用 |
| 准生产 | 验证真实数据下不出事 | 影子环境中的生产数据抽样 | 主链路是否跑通、真实客户数据是否异常 |

三段的边界不能互相串：技术测试场景里出现"符合监管要求"属于越界，业务测试场景里出现"核对 T5A_BLACK_LIST 表字段"属于越界。

工作量口径沿用模板 O 列原文：技术测试是科技外包人员自行开展技术验证的工作量；业务测试与准生产是科技外包人员**协助**业务人员测试、排查并解决问题的工时，不含业务人员编写案例与执行测试。

## 二、固定导语（逐字照抄，不得改写）

### 2.1 技术测试（三句）

```
1、梳理测试场景、编写技术测试案例；
2、开展技术测试案例评审，进一步完善测试案例；
3、技术测试人员开展技术测试工作，配合排查测试过程中遇到的环境、程序、业务规则优化等各类问题，修复后进行单元回归测试、技术回归测试。具体测试场景如下：
```

第三句是技术测试区别于另外两段的标志：它写明了"单元回归测试、技术回归测试"这一动作，不能省。

### 2.2 业务测试（两句）

```
1、为业务测试工作准备相应测试环境及系统后台基础测试数据；
2、在业务测试人员测试的过程中，对测试出现的问题进行原因排查、问题解决，具体场景如下：
```

### 2.3 准生产（两句）

```
1、为准生产测试工作准备相应测试环境及系统后台基础测试数据；
2、在业务测试人员准生产测试的过程中，对测试出现的问题进行原因排查、问题解决，具体测试场景如下：
```

注意准生产的第二句写的是"业务测试人员**准生产**测试"，比业务测试多"准生产"三字，这是两段唯一的形式差别，不要写成一样。

## 三、场景句式（五要素）

每个场景按下面的骨架展开，五要素缺一不可：

```
场景N：<角色><入口路径>，<前提数据/前置动作>，<执行动作>，查看<观察点1>、<观察点2>是否<预期>
```

| 要素 | 写法 | 正例 | 反例 |
|---|---|---|---|
| 角色 | 能发起该动作的岗位 | 分行负责人、分行操作员、总行操作员 | 用户 |
| 入口路径 | 登录系统 + 菜单两级路径 | 登录反洗钱系统，进入风险评级-新开客户审批 | 进入系统 |
| 前提 | 选定的数据类型或前置跑批 | 选择对私、对公客户评级结果从高调为低、中风险数据 | 选择数据 |
| 动作 | 一次可执行的界面操作 | 进行审批操作并提交 | 进行处理 |
| 观察点与预期 | 查看 + 具体对象 + 是否 + 明确结果 | 查看审批详情显示是否正常、审批通过后流程流转是否正常 | 查看功能是否正常 |

同一条场景可以并列多个观察点（用顿号分开），但每个观察点都必须能落到一个可见结果上。

## 四、场景从哪来：维度矩阵法

场景不是凭感觉凑的，而是从设计段与开发段逐条映射出来的。按下面的维度逐个换值，每换一个维度值就产出一条场景。

| 维度 | 取值举例 | 来源 |
|---|---|---|
| 岗位角色 | 总行操作员、分行负责人、分行操作员、无权限角色 | 设计段「权限设计」 |
| 客户类型 | 对私、对公、同业、非自然人 | 需求段业务对象 |
| 数据状态 | 新开、存量、历史、注销、潜在、黑名单命中 | 需求段状态值 |
| 风险档位 | 高、较高、中、低 | 需求段阈值 |
| 时间/批次 | 日切后、跑批后、跨评级周期、跨工作日 | 开发段定时任务 |
| 操作类型 | 查询、新增、修改、删除、审批、导出、撤回 | 功能设计 |
| 异常分支 | 空值、超限、重复提交、越权、并发 | 设计段校验规则 |
| 系统层面 | 表结构、接口报文、缓存、任务调度 | 开发段 |

**生成顺序**：先写 1 条主链路场景（P0，覆盖"正常走通"），再逐个维度换值补充分支。换值时必须改变一个维度，不能把同一维度换个说法重复写。

**裁剪规则**：两个维度值组合后业务结果完全相同（例如对公与同业走同一支逻辑）时，合并为一条并在场景里写"对私、对公"；组合后结果不同则必须拆开。

样本中的典型分支裂变：
- 同一审批动作按「对私/对公 × 新开/存量 × 高/较高 × 低/中」裂变为 4 条场景（第 71 行）。
- 同一指标任务按「新开/存量 × 对私/对公 × 指标编号」裂变为 13 条场景（第 73 行）。

## 五、三段的差异化写法

### 5.1 技术测试：必须落到技术观察点

技术测试场景的观察点要能被技术人员独立验证，鼓励出现表名、字段名、报文要素、任务名、日志标识。

```
场景1：登录反洗钱系统，进入风险评级-新开客户审批，查看查询条件和列表显示，设置不同查询条件进行查询，查看查询功能操作和结果是否正确
场景2：后台跑调整逻辑后的PGS50007指标任务，任务结束后进入新开客户评级，查询公式为"新开对私客户为我行高风险对公客户的法定代表人、受益所有人"的客户，查看客户详情核对是否剔除掉关联对公客户核心状态是潜在和注销的
```

可用的技术观察点清单：表结构与索引是否与设计一致、字段取值与回填是否正确、报文组包字段与码值是否正确、解析结果是否正确、任务跑批结果是否落库、缓存是否刷新、日志能否按流水号追溯、越权是否被拦截。

### 5.2 业务测试：必须落到业务口径

业务测试场景**不得出现表名与字段名**，观察点要写成业务人员能判断的结果。

```
场景1：分行部分负责人进入新开客户审批，选择对私、对公客户评级结果从高调为低、中风险数据，进行审批操作，查看审批详情显示是否正常、审批通过、审批通过流程流转是否正常
```

样本中业务测试与技术测试的场景**逐条相同**（22 条里有 17 条完全一致，另 5 条业务测试场景数为技术测试的子集）。这是因为业务人员复核的正是技术人员验证过的路径，只是判断标准从"程序对不对"变成"业务上通不通"。

因此写作规则是：**先写技术测试场景，再派生业务测试场景**。派生两步：删去纯技术动作（跑批、直查数据库、报文比对）；把技术观察点改写为业务观察点。

### 5.3 准生产：短、准、只挑主链路

准生产的场景最短，通常每行 1–5 条，只覆盖真实数据下最容易出问题的主链路。

```
场景1：分行负责人进入新开客户审批，查询较高及以上客户等级的客户数据，进行审批处理
场景2：分行操作员进入评级结果查询，查看不同风险等级客户的下一次评级周期
```

准生产场景不带技术观察点，也不写"查看是否正确"，只写"做什么、看什么"。这是三段中最简洁的一段，不要照搬技术测试的长句式。

## 六、场景数怎么定

**不按人天倒推场景数**。样本中 5.25 人天的功能写了 17 条场景，18.5 人天的功能写了 13 条场景，两者不成正比——场景数取决于需要验证的独立分支数，人天取决于改造深度。

样本 22 条功能行的场景数分布：最少 1 条，最多 17 条，均值 5.95，中位数 4。

| 功能特征 | 建议场景数 |
|---|---|
| 单字段增补、单校验调整 | 1–3 |
| 单页面多查询条件 | 3–6 |
| 多分支业务规则（按客户类型、风险档位裂变） | 6–12 |
| 跨系统报文、多模块联动、多指标 | 10–17 |

业务测试场景数**不得超过**技术测试场景数（样本中 17 条相等、5 条为子集），准生产为 1–5 条。

## 七、覆盖自查清单

每条功能行写完技术测试场景后，逐项确认是否已覆盖（不适用的划掉并说明原因）：

- [ ] 表结构与索引、字段取值
- [ ] 查询条件组合与列表显示
- [ ] 新增/修改/删除的保存与回显
- [ ] 校验与拦截提示（必输、重复、超限）
- [ ] 状态流转与流程节点
- [ ] 权限：功能权限 + 数据权限（跨机构）
- [ ] 留痕与日志可追溯
- [ ] 跑批/定时任务结果
- [ ] 接口报文组包与解析
- [ ] 导出/报表数据一致
- [ ] 异常与边界（空数据、超限、重复提交）

## 八、禁止写法

| 禁止 | 原因 | 改成 |
|---|---|---|
| "查看功能是否正常" | 无观察点，不可执行 | 查看列表字段、分页、排序是否正确 |
| "验证系统稳定性、兼容性" | 不属于本期功能测试范围 | 删除，或落到具体操作 |
| "测试相关功能""等模块" | 范围不闭合 | 写明具体菜单与动作 |
| 技术测试写"符合监管要求" | 越界到业务口径 | 改到业务测试 |
| 业务测试写表名、字段名 | 越界到技术实现 | 改写为界面可见的业务名词 |
| 场景编号跳号、重号 | 与 Word 测试要点对不上 | 从 1 连续编号 |
| 改写三段固定导语 | 与公司模板口径不符 | 逐字照抄第二节 |
| 场景数按人天凑 | 会导致场景空泛或注水 | 按第四节维度矩阵推导 |

## 九、与 Word「6) 测试要点」的对应

Word 的测试要点是**模块级**汇总，Excel 的技术测试是**功能行级**明细。两者关系：

1. Word 测试要点条数一般少于该模块所有功能行场景数之和，做法是从各功能行场景中挑选模块级关键路径；
2. Word 测试要点同样使用 `场景N：` 句式，编号从 1 开始连续；
3. Word 测试要点中不得出现 Excel 技术测试里没有的测试对象；
4. 模块只有一个功能行时，Word 测试要点应与该功能行的场景基本一致（可略作归并）。

## 十、完整样例（脱敏自样本第 71 行）

技术测试：

```
1、梳理测试场景、编写技术测试案例；
2、开展技术测试案例评审，进一步完善测试案例；
3、技术测试人员开展技术测试工作，配合排查测试过程中遇到的环境、程序、业务规则优化等各类问题，修复后进行单元回归测试、技术回归测试。具体测试场景如下：
场景1：登录反洗钱系统，进入风险评级-新开客户审批，查看查询条件和列表显示，设置不同查询条件进行查询，查看查询功能操作和结果是否正确
场景2：分行负责人进入新开客户审批，选择对私、对公客户评级结果从高调为低、中风险数据，进行审批操作，查看审批详情显示是否正常、审批通过后流程流转是否正常
场景3：进入评级结果调整，发起评级调整，进入存量客户评级进行流程处理，查看操作是否正常，流程记录是否正确
```

1、为业务测试工作准备相应测试环境及系统后台基础测试数据；
2、在业务测试人员测试的过程中，对测试出现的问题进行原因排查、问题解决，具体场景如下：
场景1：分行负责人进入新开客户审批，选择对私、对公客户评级结果从高调为低、中风险数据，进行审批操作，查看审批详情显示是否正常、审批通过后流程流转是否正常
```

准生产（只留主链路）：

```
1、为准生产测试工作准备相应测试环境及系统后台基础测试数据；
2、在业务测试人员准生产测试的过程中，对测试出现的问题进行原因排查、问题解决，具体测试场景如下：
场景1：分行负责人进入新开客户审批，查询较高及以上客户等级的客户数据，进行审批处理
